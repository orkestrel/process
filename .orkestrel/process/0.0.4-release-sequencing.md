Measured 2026-08-19 against the registry and the regenerated catalog, not inferred from a document.

## Who depends on this package at runtime

Two packages, and both matter because a runtime range is published surface:

```text

	"@orkestrel/process": "^0.0.3",
```

and from the catalog `scaffold overwrite` regenerated:

```text
| `@orkestrel/mcp` | `0.0.19` | L3 | … `@orkestrel/process` `^0.0.3` … |
```

## The cascade a 0.0.4 publish sets off

`AGENTS.md` § Publishing: a runtime `dependencies` bump reaches every consumer, so each one re-pins,
re-runs its gates, bumps, and republishes in layer order.

1. **`process` 0.0.4** publishes.
2. **`mcp`** re-pins `@orkestrel/process` to `^0.0.4`, bumps to 0.0.20, republishes.
3. **`scaffold`** re-pins the same range, bumps to 0.0.45, republishes. This is the expensive one:
   `scaffold` is a devDependency of **every** fleet package, so its release starts a propagation wave
   that re-pins `@orkestrel/scaffold` across all of them.
4. **`probe`** reaches `process` transitively through `mcp` and directly through `scaffold`'s vendored
   host. It is unpublished, so it re-pins and needs no release of its own.

`supervisor` consumes `process` directly and re-pins on its own next dependency pass.

## The recommendation

Publish `process` 0.0.4 and `scaffold` 0.0.45 in **one window**, in that order, with `mcp` 0.0.20
between them. Discovering the cascade after the first upload costs a second approval and leaves the
fleet split across two `process` versions in the meantime — and two ranges that disagree install two
copies of one package, which the compiler reads as two distinct types.

This is not a reason to hold 0.0.4. It is a reason to sequence it.

## Probe's version

`@orkestrel/probe` is **unpublished**:

```text
$ npm view @orkestrel/probe versions
npm error 404 '@orkestrel/probe@*' is not in this registry.
```

Its first publish is therefore 0.0.1, and it stays at 0.0.1. Bumping before a first publish burns a
version that never existed.

## What is not decided here

Publishing is the owner's decision and the owner's credential. This file prepares the order; it
authorizes nothing.

## The rename made the wave mandatory, 2026-08-20

PC7 renamed the one-shot execution primitive: `run` to `execute`, `runSync` to `executeSync`, and
`RunResult`, `RunInput`, `RunOptions`, and `RunSyncOptions` to their `Execute*` forms. That moves the
published surface, so the wave is no longer optional sequencing — it is the only way any consumer
reaches the new names.

Measured cross-package usage of the renamed surface, taken from each checkout:

| Consumer | Uses the renamed surface | State |
| -------- | ------------------------ | ----- |
| `@orkestrel/mcp` 0.0.19 | none | No re-pin obliged by the rename |
| `@orkestrel/scaffold` 0.0.44 | `runSync`, at one import and one call in `src/bin/CLI.ts` | Updated to `executeSync` in `e375a3c` |
| `@orkestrel/sea` 0.0.9 | not checked from this container | Check before the wave |

### The standing consequence, which is a real one

`@orkestrel/scaffold`'s branch imports `executeSync`, which exists only in the unpublished 0.0.4. Its
manifest pins `^0.0.3` and its lockfile resolves 0.0.3, so a clean `npm ci` there installs a package
without that export and its typecheck fails. The working checkout passes only because the locally
built 0.0.4 tarball is installed over the resolved version.

There is no code fix for this, and a compatibility branch is forbidden. It closes when 0.0.4 reaches
the registry and scaffold re-pins to `^0.0.4`, which is the wave's first two steps in order.

### Order

1. `@orkestrel/process` 0.0.4 publishes.
2. `@orkestrel/scaffold` re-pins to `^0.0.4`, installs, proves its gates, bumps, publishes.
3. `@orkestrel/mcp` and `@orkestrel/probe` follow on their own account, per the layer order the
   catalog table regenerates.

Publishing is the owner's decision and the owner's credential.
